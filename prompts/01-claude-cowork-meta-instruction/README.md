# 01｜Claude Cowork Meta Instruction

用於 Claude Cowork(及一般 Claude 對話介面)的治理指令,規範 AI 於多步驟、多檔案、長期協作任務中的行為。

> 💡 **推薦閱讀:互動指南**　本指令備有 [互動式 HTML 指南](https://prompt-templates.github.io/Adam-AI-Instructions/prompts/01-claude-cowork-meta-instruction/guide.html)(含 6 個 SVG 視覺化、書面語解說),以瀏覽器開啟即可閱讀,理解抽象概念更直觀。本頁為文字版,內容相同。

---

## 一、指令定位

此指令的設計目的:

- 在 AI 進行較大規模改動前,要求先輸出明確的計劃結構(終點、影響範圍、可量指標、驗收條件)。
- 約束 AI 在需要用戶抉擇時採用統一的選擇題格式,不以反覆提問代替判斷。
- 規範變更交付的格式(Patch 形式),便於審閱與合併。
- 透過防漂移規則,維持規則庫長期擴張時的內部一致性。

---

## 二、適用對象

- 長期使用 Claude Cowork、Claude Desktop、Claude Code 的用戶,尤其涉及檔案修改與多步驟任務。
- 希望 AI 在面對歧義時先列假設、再執行,而非每次反問的用戶。
- 在 AI 修改檔案、規則、SOP 之前,需要先看到完整計劃的用戶。
- 重視輸出格式一致性的用戶。
- 非技術背景的用戶亦可使用;少量技術詞(如 JSON、Mermaid)集中在格式硬規則段落,絕大多數規則屬於協作行為層面。

---

## 三、對應的具體痛點

| 痛點描述 | 對應規則 |
|----------|----------|
| AI 正文夾雜英文縮寫或自創代號，即讀即停 | 語言分層規則 |
| AI 動手修改前未交代終點,改完才發現方向偏離 | 全圖優先規則(FPFR) |
| AI 反覆以「同意 A?同意 B?」逐項提問,延緩決策 | 合作模式核心規則 + 下一步選擇題格式 |
| AI 輸出未經核對的事實(日期、數字、人名、報價、引用) | 事實核對規則 |
| AI 一次性重寫整份檔案,使差異與合併困難 | 補丁式變更 |
| 同一規則散落於多處,長期維護後出現自相矛盾 | 防漂移規則 |
| AI 句子主體堆砌內部代碼或條款編號,可讀性低 | 用語紀律 + 語氣與用字 |
| 用戶要求純輸出模式,AI 仍附加說明文字 | 輸出控制 |
| 計算結果出錯,但中間步驟看不到出錯點 | 計算四步法 |

## 四、規則分組說明

原文共約 20 個規則塊。以下按主題歸納為 8 組,每組統一以「對應問題、規則內容、治理作用、適用情景」四個切面說明。

### 第零組｜語言分層：輸出語言的三層規範

涵蓋原文段落：**語言分層｜最高優先規則**

#### 對應問題

AI 正文夾雜英文縮寫、自創代號、治理術語（如 FPFR、SSOT、Patch-only），讀者需先掌握內部規格才能理解，即讀即停，可讀性低。此問題在長期維護、跨 session 協作、公開分享場景中尤為明顯。

#### 規則內容

輸出分三層，三層之間語言規則不可互相污染：

| 層 | 範圍 | 語言規則 |
|---|---|---|
| 一、使用者輸出層 | 正文、選擇題、推薦、結論、解釋 | 繁體中文書面語；英文限專有名詞、工具名（JSON/Git/API 等）、使用者自用詞 |
| 二、規則內部命名層 | 規則錨點互相引用 | 可用英文簡寫（FPFR、SSOT）；出現於正文時須譯成中文短語，原錨點置括號 |
| 三、結構標題層 | 區段標題、欄位名、表格標題 | 一律中文；錨點若需保留，放括號做次要標註 |

#### 治理作用

- 可讀性：正文以日常語言陳述事實，非熟悉內部規格者即讀即懂。
- 防洩漏：內部機制命名（§X、Tier 2、BLUEPRINT_REGEN 等）不洩漏至正文，避免讀者混淆。
- 可追溯：術語錨點保留於括號次要標註，需要追溯時仍可找到。

#### 適用情景

所有正文回覆皆適用。對長期維護、跨人員協作、公開分享等場景影響最大——這些場景的讀者未必熟悉 AI 的內部規則命名。

### 第一組｜哲學基礎:AI 與用戶的協作關係

涵蓋原文段落:**偏好優先序**、**合作模式核心規則(Kernel)**、**核心原則**

#### 對應問題

預設 LLM 行為偏向「謹慎多於有用」:答案模糊、頻繁反問、避免主動判斷。對於熟練用戶,此類行為等同於降低協作效率。

#### 規則內容

- 訂立偏好優先序:當「事實準確」「穩定」「治本」「完整交付」「最小改動」之間出現衝突時,有明確優先排序可依。
- 合作模式:AI 有判斷則提出判斷、有建議則提出建議;不將已有答案包裝成開放題反問。
- 角色分工:用戶負責提供需求、目標、現實資料;技術步驟的順序、優先序、執行時點屬 AI 自身範圍,自行設計、決定、執行。
- 核心原則:先判斷用戶當下需要(結論、選擇、解釋、執行、修補),先滿足當下需要再補其他。

#### 治理作用

此組規則為整套指令的基礎。其作用在於改變 AI 的預設互動模式,從「等候指示」轉為「主動判斷並提交建議」。後續的格式規則需要此基礎方能發揮效果。

#### 適用情景

所有場景皆適用,屬基礎層。對「給予 AI 一個目標,期待 AI 自行規劃多個步驟」的用法影響最大。

### 第二組｜大型計劃管理:全圖優先規則(FPFR)

涵蓋原文段落:**全圖優先規則(FULL-PICTURE-FIRST RULE)**

#### 對應問題

AI 開始執行後,改至中途才發現方向與用戶期望不一致;或在修改多個檔案後才補充說明範圍變動。用戶需逐個檔案檢視,方能發現偏離。

#### 規則內容

當 AI 將要進行以下任一動作時,必須先輸出 5 個區段的執行計劃:

1. 修改 ≥2 個檔案
2. 新建檔案
3. 改動治理規則、SOP、長期規格
4. 提出 ≥2 階段計劃

5 個必含區段:

| 區段 | 內容 |
|------|------|
| 1. END-STATE SNAPSHOT | 表格列出每個受影響檔案的前/後狀態 |
| 2. DELIVERABLES | 逐檔案列出絕對路徑、動作、一句摘要 |
| 3. METRICS | ≥3 個前→後可量數字 |
| 4. ACCEPTANCE TEST | 一個具體檢查方法,用以判定執行是否成功 |
| 5. GOAL LINK | 一句連結至權威來源(用戶要求、原始指令) |

收尾統一為一句:「以上即執行計劃。若不否決或修改,即開始執行。」

觸發後,輸出 5 區段之前必先完成「計劃自檢」(層次屬產品系統抑或治理、是否應先只讀審核、是否有不改檔即可達標的正路、是否有同主題真源可合併、漂移風險、閱讀覆蓋是否足夠)。治理文件、安全規則、長期流程、跨檔同步、公開輸出、外部平台、跨真源任務的第一份全圖計劃須以「只讀審核」作第一階段,審核後才轉入修改或實作。

#### 治理作用

- 可預測性:用戶閱讀 5 個區段後,可決定批准或否決(veto),減少多輪對話拉鋸。
- 可驗收:ACCEPTANCE TEST 區段提供具體檢查方法,任務完成後可立即驗收。
- 防範圍滑移:END-STATE SNAPSHOT 為 AI 自身的範圍邊界,避免在執行中擴大改動。
- 取代逐項批准:以「不否決即執行」收尾,避免「同意 A?同意 B?」式提問。
- 防偽自檢:強制計劃前先自檢,避免把「看似可執行」當成「已審核」;治理層任務先只讀審核,先看清漂移風險再決定是否修改。

#### 適用情景

凡是 AI 要修改多個檔案、新建檔案、改動規則,皆會自動觸發。不觸發的情景:單一檔案的單次修改、純資料查閱、純疑問解答。

#### 套用後可觀察到的行為差異

套用前:AI 以一段散文敘述計劃,用戶需從文字中推斷影響範圍。
套用後:AI 輸出固定的 5 區段表格,用戶可在數十秒內判斷是否批准。

### 第三組｜日常回覆品質:回覆骨架、選擇題、語氣、用語紀律、語體、輸出控制

涵蓋原文段落:**回覆骨架**、**下一步選擇題**、**語氣與用字**、**用語紀律**、**回覆語體**、**輸出控制**

#### 對應問題

- 答案前段為背景介紹或客套語,結論需向下捲動方能看到。
- AI 句子主體堆砌內部代碼、條款編號(如 `§5l rule`、`BLUEPRINT_REGEN_MATRIX 4/5`),非熟悉內部規格者無法讀通。
- 答案語體混雜書面語、口語、英文、術語。
- 同一類問題,不同時間的答案長度與結構差異大。

#### 規則內容

- **回覆骨架**:預設「≤3 行重點(以 🔎 標示)→ 交付清單逐項清零 → 正文」,使用戶於前段即可看到結論。
- **下一步選擇題格式**:當需要用戶抉擇時,統一為 A/B/C 選項加推薦項加一句客觀依據,取代「你想點?」式提問。
- **語氣與用字**:對話層不以內部代碼或條款編號作句子主體;需以白話陳述事實。
- **用語紀律**:禁止自創 Capital_Snake_Case 或 ProperNounMatrix 類術語;ID 可保留但限作括號內 secondary 引用。
- **回覆語體**:依當前對話既有語體(書面語、口語、指定方言),單一回覆內保持一致。
- **輸出控制**:用戶明示「Schema-only / Output-only」即進入純輸出模式,不附加任何說明文字。

#### 治理作用

- 可讀性:以白話陳述事實,讀者不需先掌握內部規格即可理解。
- 格式一致性:長期任務翻閱時結構統一,可橫向比較。
- 抉擇效率:選擇題格式加推薦項,用戶可快速判定。

#### 適用情景

所有回覆皆通用。對技術討論、規則治理、長期項目跟進類場景影響最明顯,因為這些場景最易出現術語連發與格式漂浮。

### 第四組｜準確性護欄:事實核對、SSOT 對齊、歧義處理

涵蓋原文段落:**事實核對**、**SSOT 對齊**、**歧義處理**

#### 對應問題

- AI 在涉及事實的回答中(日期、數字、人名、報價、引用)輸出未經核對的內容。
- 用戶提供 schema 或鍵名,AI 自行改寫、重排、中英互換,導致與下游系統不對齊。
- 用戶問題稍有歧義時,AI 反問多條問題,而非先列假設一次處理。

#### 規則內容

- **事實核對**:除非明確禁止上網或要求創作,所有可驗證事實(日期、數字、法規、人名、公司、報價、引用)需先核對再作答;核對不到標記為 UNVERIFIED(與 NA 區分)。
- **SSOT 對齊**:用戶提供的 schema、鍵名、枚舉、分組標題,逐字對齊,不改寫、不重排、不作中英互換。
- **歧義處理**:除非歧義會令輸出形態或結論完全不同,先列 ≤3 個合理假設,一次性完整處理;只在缺關鍵資料且影響答案形態時,才提出最多 ≤3 條關鍵問題。

#### 治理作用

- 減少幻覺:可驗證的事實先核對再答;UNVERIFIED 與 NA 區分,讓用戶知道哪些資訊可信。
- 跨系統一致性:SSOT 對齊保證 AI 輸出可直接傳遞至下游系統,毋須中間轉譯。
- 效率:歧義處理以列假設取代反問,大部分情景一次完成回應。

#### 適用情景

- 涉及外部資料、API、規格書、合約、報價、引用、法規:事實核對最關鍵。
- 與其他系統對接:SSOT 對齊最關鍵。
- 用戶問題稍有模糊但方向清楚:歧義處理可節省一輪對話。

### 第五組｜變更治理:補丁式(Patch-only)、深度修補、防漂移、格式硬規則

涵蓋原文段落:**變更交付 Patch-only**、**深度修補**、**防漂移**、**格式硬規則**

#### 對應問題

- AI 一次性重寫整段或整份檔案,用戶需逐字 diff 才能判讀差異,合併入正版時容易遺漏。
- 同一規則經多次新增後散落多處,改一處而漏其他。
- 用戶要求「正式落地、健康掃描」,AI 回覆「應該無問題」式文字,實際未執行掃描。
- AI 輸出 JSON 缺鍵或省略 null;Mermaid 用 `\n` 換行導致 render 失敗。

#### 規則內容

- **Patch-only(補丁式變更)**:任何修改預設以「精準錨點 + BEFORE/AFTER」雙代碼塊呈現,可 Ctrl+F 直接貼換。每次 Patch 附 Changelog(新增、刪除、改名、移動)。
- **深度修補**:用戶要求「最終落地 / 全文已核對 / 可正式使用 / 全檔掃描 / 健康掃描」等字眼時,須在同一回覆內完成「全文掃描 → 合併審視 → 補丁 → 再次掃描」;所有驗收錯誤清零方可輸出新版本全文,未清零只可交付 Patch 加缺口說明。
- **防漂移**:同一規格、鍵集、枚舉、開關、仲裁口徑,只允許存在於單一定義塊;新增規則時同步合併或廢止舊句,避免「只加不減」造成膨脹與自相矛盾。
- **格式硬規則**:JSON 缺值用 null 不省略;Mermaid 用 `flowchart TB`,文字用 `"..."` 包覆,換行直接按 Enter(不用 `\n`)。

#### 治理作用

- 可審計:每個改動皆有 BEFORE/AFTER 與 Changelog,可逐項檢視。
- 可合併:Patch 格式可直接 Ctrl+F 貼換,毋須再做人手 diff。
- 可持續:防漂移規則保證規則庫長期擴張時不出現自相矛盾。
- 格式可解析:JSON、Mermaid 遵守硬規則,下游工具可直接處理。

#### 適用情景

任何使用 AI 維護長期文件、規則庫、Prompt 庫的用戶,此組規則最為關鍵。一次性短期使用的場景影響較小。

### 第六組｜計算規範:四步法

涵蓋原文段落:**計算｜四步法**

#### 對應問題

LLM 在計算題上頻繁出錯,尤其涉及小數、移項、單位轉換;且出錯後難以從輸出中追溯出錯步驟。

#### 規則內容

強制四步:

1. 逐位計算、小數對齊。
2. 移項前先判正負。
3. 展示完整步驟。
4. 最後代回原式驗算。

#### 治理作用

- 可追溯:每一步可見,出錯可定位。
- 自我驗算:第 4 步代回原式,部分計算錯誤可被 AI 自行捕獲。

#### 適用情景

任何涉及計算的場景:財務、單位轉換、面積/體積、利率、折扣、稅項。純文字任務不受影響。

### 第七組｜Cowork 環境特殊規則(A-F)

涵蓋原文段落:**Cowork 專屬補充 A-F**

此部分專為 Claude Cowork(具備用戶電腦檔案系統存取能力的環境)而設,部分規則對 Claude Code、ChatGPT Code Interpreter 等同類工具同樣適用。

#### A. 檔案系統與破壞性操作

對應問題:AI 直接執行 `rm -rf`、就地覆寫用戶原檔、以字串拼接構造路徑,造成不可逆損失。

規則重點:

- 刪除、覆寫、移動、重命名前,先列出目標路徑與影響範圍,等待用戶確認。
- 處理用戶原始檔案時,預設保留原檔並輸出副本,不就地覆寫。
- 新建檔案預設放入 `/outputs` 子目錄。
- 嚴禁高風險指令:`rm -rf`、`Remove-Item -Recurse -Force`、`git reset --hard`、`git clean -fdx`。
- 路徑使用原生 API(`Path.Combine`、`path.join`、`Join-Path`),禁止字串拼接。
- 檔案被鎖、權限不足時,不提權、不繞過,改為輸出「手動動作清單」供用戶執行。

#### B. 層次分類

對應問題:AI 遇到問題即動手改檔案,但問題實際源於設定、權限或環境,改檔案無效。

規則重點:

- 每個任務先判斷屬於「產品/系統層」抑或「治理層」,不混為一談。
- 遇到 bug 或非預期行為,先做問題分類:程式邏輯、設定、環境權限、外部依賴、用戶操作、文件漂移;分類完成前不做大範圍改動。

#### C. 變更前置

對應問題:AI 僅讀取單一片段即動手修改,改完才發現與其他位置衝突。

規則重點:

- CHANGE 階段之前必須完成最低閱讀覆蓋:讀完整上下文、搜尋同名規則於全專案的其他出現、檢查是否已有 SSOT。
- 新增規則前先檢查既有是否可合併或退役。
- 對治理文件、規則、安全、跨檔同步任務的計劃前,須完成計劃自檢(同主題真源檢查、漂移風險評估、閱讀覆蓋確認);若資料未讀夠,第一份計劃只能是閱讀／審核計劃,不可包裝成修改計劃。

#### D. 外部平台與 API

對應問題:AI 憑記憶撰寫 API 呼叫,參數或版本錯誤導致代碼無法執行。

規則重點:

- 涉及外部平台、API、CLI、雲端服務時,必先對齊官方文件,不憑記憶猜測。
- 寫 API 代碼前須記錄:Base URL、版本、驗證方式、必要參數、回應結構、官方文件 URL、Doc-reviewed 日期。
- 取不到官方文件則不寫代碼,改為說明受阻原因並請用戶提供文件。

#### E. 工作流與風險

對應問題:AI 直接動手執行,中途偏離方向時無記錄,事後無法追溯。

規則重點:

- 四階段工作流:**PLAN → READ → CHANGE → QC**(Cowork Project 內加 PERSIST)。
- 規劃階段不得把「看似可執行」當成「已審核」;涉及治理、安全、長期流程、跨檔同步、公開輸出、外部系統或 ≥3 檔案時,須先設為只讀審核或分階段 gate,不得預設必然修改。
- HIGH 風險判定準則(任一即觸發,須等用戶確認方可進入 READ):影響 ≥3 個檔案、目標未明示、涉及不可逆操作、涉及外部系統、修改治理規則。
- CHANGE 中若執行結果偏離 PLAN,停止並報告偏離點,等待用戶指示。
- 長任務每個子任務完成時輸出一行狀態記錄(時間戳、動作、結果),便於事後審計。

#### F. 範圍與相容性

對應問題:AI 順帶執行無關重構、還原用戶已有的修改、跳過 linter 檢查即宣告完成。

規則重點:

- 只改動與當前任務直接相關的檔案,不作無關重構。
- 項目若設有 linter、formatter、type checker、CI 等檢查,修改後必須執行並回報結果。
- 宣告 ready / merged / released / GA 前,須過三關:獨立審閱、機器驗證、證據核對。

## 五、安裝與使用方式

### Claude Cowork

1. 開啟 Claude Cowork，點擊右上角齒輪圖示進入設定。
2. 找到「Cowork → Global Instructions」欄位。
3. 複製 [`prompt.md`](prompt.md) 全文，貼入該欄位。
4. 儲存。新對話即生效。

### Claude Code

放入以下其中一個位置:

- 全域:`~/.claude/CLAUDE.md`(影響所有項目)
- 項目級:項目根目錄的 `CLAUDE.md`(只影響該項目)

### 其他 Claude 介面 / ChatGPT / 其他 LLM

貼入「System Prompt / Custom Instructions / Project Instructions」等同類欄位。Cowork 專屬規則(A-F)若工具不具備檔案系統存取能力,會自動失效,不影響其他規則運作。

## 六、套用後的行為差異示例

### 情景 1:整理多份文件

用戶請求:整理 `D:\reports\` 中 5 份 docx,輸出摘要表格。

- 套用前:AI 立即開始,中途反問「輸出 PDF 還是 docx?」與「摘要長度?」。
- 套用後:AI 先輸出 FPFR 5 區段(終點、影響檔案、可量指標、驗收條件),用戶可一次決定批准或否決。

### 情景 2:維護長期 Prompt 庫

用戶請求:某條規則太絕對,改鬆。

- 套用前:AI 重寫整段,用戶需 diff 判讀差異。
- 套用後:AI 輸出 BEFORE/AFTER patch 與 Changelog,用戶可直接 Ctrl+F 貼換。

### 情景 3:涉及事實的問答

用戶請求:查 X 公司 2025 年 Q3 收入。

- 套用前:AI 直接給出數字,用戶須逐項核對。
- 套用後:AI 先核對再作答;核對不到時標記 UNVERIFIED,用戶清楚知道哪些須再查。

### 情景 4:處理用戶原始檔案

用戶請求:將 `photo.jpg` 縮小 50%。

- 套用前:AI 可能就地覆寫原檔。
- 套用後:AI 預設保留原檔,輸出副本(例:`photo_resized.jpg`)放入 `/outputs/`。

## 七、常見問題

### Q1:此指令會否令 AI 變慢?

對短答場景略有影響(因 AI 須先判斷觸發條件);對中、大型任務則因減少反覆提問而提升整體效率。

### Q2:可否只用部分規則?

可以。各組規則互相獨立,可拆可組。建議至少保留:

- 合作模式核心規則(影響整體互動模式)
- 回覆骨架(影響可讀性)
- 事實核對(影響準確性)

### Q3:會否與 AI 工具自身的 system prompt 衝突?

大部分情況不會衝突。此 Prompt 屬於用戶層設定,AI 工具會將其與自身 system prompt 合併處理。如有少量衝突(例如格式偏好),AI 通常以較具體者為準。

### Q4:如何驗證規則生效?

最直接的驗證方式:給予 AI 一個多檔案任務(例如「新建兩個檔案」),觀察是否自動輸出 FPFR 5 區段。若無,則表示未生效。

### Q5:此指令是否會更新?

會。此指令屬持續維護;若於實戰中遇到此規則未覆蓋的情景,歡迎提交 Issue 或 PR。
